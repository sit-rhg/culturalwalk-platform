# 开发环境与协作

## 1. 五分钟跑起来

前置：Docker Desktop、Node 24.x、pnpm 12.x、Python 3.12.x（或用 Dev Container 免装）。

```bash
git clone <repo-url> culturalwalk-platform
cd culturalwalk-platform

# 1) 起依赖（Postgres + MinIO）
docker compose -f infra/docker-compose.yml up -d db minio

# 2) 后端
cd services/api
python -m venv .venv && . .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cp ../../infra/.env.example .env
alembic upgrade head
uvicorn app.main:app --reload --port 8000
# 打开 http://localhost:8000/docs 应看到全部 tag

# 3) 前端
cd ../../apps/web
pnpm install
pnpm dev
# 打开 http://localhost:5173
```

验收：`curl localhost:8000/api/v1/health` 返回 `{"status":"ok"}`，前端首页不报错。

### 工具链版本（以 CI 为准）

CI 是唯一的版本基线，本地尽量保持一致：

| 工具 | 基线 | 检查 |
|---|---|---|
| Node | 24.x（见 `.nvmrc`） | `node -v` |
| pnpm | 12.5.1（CI 固定） | `pnpm -v` |
| Python | 3.12.x（见 `.python-version`） | `.venv/bin/python -V`（Windows：`.venv\Scripts\python.exe -V`） |
| PostgreSQL | 16（`docker compose` 起） | 本地 SQLite 只够快速试跑，不能当验收环境 |

切换版本：

```bash
# Node 24（仓库根 .nvmrc）
nvm install && nvm use        # 或 fnm use / mise use

# pnpm 12.5.1
npm i -g pnpm@12.5.1
```

Python 3.13/3.14 没在 CI 验证过；系统 `python3` 是 3.10 时，显式用 `python3.12 -m venv .venv`。

**lockfile 纪律**：`pnpm-lock.yaml` 的 `lockfileVersion` 是 9.0。pnpm 大版本升级可能顺手改写整份 lockfile——PR 里看到它整片变动先 revert，再用 CI 同版本的 pnpm 重装。

### 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 端口 5432 被占 | 本机已有 Postgres | 改 `infra/.env` 的 `DB_PORT` |
| `alembic upgrade` 报 relation 不存在 | 库连错 | 检查 `DATABASE_URL` |
| 前端跨域失败 | 没配代理 | `vite.config.ts` 已代理 `/api` → 8000，别改端口 |
| `pnpm gen` 报 schema 错 | openapi.yaml 语法错 | `python -c "import yaml;yaml.safe_load(open('docs/api/openapi.yaml'))"` |
| 双击启动器没反应 | 没有执行权限，或被 Gatekeeper 拦 | 右键 → 打开，或 `chmod +x "启动 CultureWalk.command"` |
| `pnpm -v` 不是 12.x | 装过旧版全局 pnpm | `npm i -g pnpm@12.5.1` |

## 2. 目录约定

```
services/api/app/
├── main.py              组装：注册路由、异常处理、中间件
├── core/                跨模块基础设施（配置、DB 会话、错误、鉴权依赖）
└── modules/<模块>/
    ├── router.py        只做 HTTP 编解码，不写业务
    ├── service.py       业务规则（唯一放规则的地方）
    ├── repository.py    SQL / ORM 查询
    ├── models.py        ORM 表定义
    ├── schemas.py       Pydantic DTO
    └── tests/           模块测试，必须能独立跑
```

**四条铁律**

1. 模块之间只调 `service`，不 import 别人的 `models`
2. 不在 `router.py` 写 if/else 业务判断
3. 不在 `repository.py` 写权限判断
4. 一个模块的测试不能依赖另一个模块的实现（用 fake）

## 3. 分支与提交

```
main                      受保护，只能通过 PR 合入
feat/<模块>/<短描述>       例：feat/routes/version-freeze
fix/<模块>/<短描述>
docs/<短描述>
```

提交信息：

```
<模块>: <做了什么>

例：routes: 草稿提交时冻结版本并计算内容 hash
    moderation: 审核任务改为租约抢占，修复双人审核
```

- 一个 PR 只对应 `docs/01-模块与任务看板.md` 里的一张卡
- PR 存活 ≤ 3 天，超了就拆
- PR 描述必须贴验收命令和输出

## 4. Code Review 要点

| 看什么 | 不合格的例子 |
|---|---|
| 权限在后端 | 前端隐藏按钮就当作有权限 |
| 状态机 | 直接 `status = 'published'` 跳过 publication 表 |
| 事务 | 提交审核分三次 commit |
| 错误包 | `raise HTTPException("出错了")` |
| 契约 | 改了返回字段却没改 openapi.yaml |
| 测试 | 只有 happy path |

## 5. 测试要求

| 层级 | 覆盖什么 | 命令 |
|---|---|---|
| 单元 | service 的业务规则、状态机非法流转 | `pytest app/modules/<m>/tests -q` |
| 接口 | 每个端点的 2xx + 至少一个 4xx | `pytest tests -q` |
| 权限负例 | 每条 403/401 都要有用例 | `pytest tests/test_authz.py -q` |
| 端到端 | 主链路 5 步 | `pnpm test:e2e` |

覆盖率不是目标，**负例是目标**。一个新端点至少要有「未登录」「无权限」「状态不对」三个用例之一。

## 6. CI 做什么

`.github/workflows/ci.yml` 在每次 PR 上跑（前端 job 固定 Node 24 + pnpm 12.5.1，后端/契约 job 固定 Python 3.12）：

1. `ruff check` + `ruff format --check`
2. `mypy app`（不要求全绿，新代码必须无新增错误）
3. `pytest -q`
4. `pnpm lint && pnpm typecheck`
5. `pnpm gen --check`（契约与生成类型是否一致）
6. `docker compose config`（compose 语法）

任何一项红 = 不能合。

## 7. AI 辅助开发的边界

| 让 AI 做 | 不要交给 AI |
|---|---|
| 按任务卡写 CRUD、DTO、组件 | 决定状态机怎么流转 |
| 补测试用例（给它负例清单） | 判断「这个功能算不算完成」 |
| 写迁移草稿 | 执行迁移（迁移只由 P3 跑） |
| 解释报错、写文档 | 决定要不要加新表 / 改契约 |

用过 AI 的 PR，作者必须在描述里写一句「AI 生成了哪部分，我改了什么」。

## 8. 任务认领流程

1. 在 `docs/01-模块与任务看板.md` 找到状态为 `待认领` 的卡
2. 群里说一句「我要 `RT-03`」，把该行状态改成 `进行中 @你的名字`
3. 建分支 `feat/routes/version-freeze`
4. 先写测试（或先写失败用例），再写实现
5. 本地跑通验收命令，贴输出
6. 提 PR，找一个人 review
7. 合并后把状态改成 `已完成`

**冲突预防**：两人绝不改同一个模块目录。跨模块改动必须先找 P1 拆卡。

## 9. 数据库迁移编号怎么取

`services/api/migrations/versions/` 里的编号是**全局唯一、严格串行**的一串：每份迁移的 `down_revision` 指向上一份。
两个人同时开新表就会撞同一个号——2026-11-02 就撞了一次：catalog、identity、planner 三份迁移都叫 `0003`，
各自的分支单看都没问题，两条一合进 main 就变成两个 head，`alembic upgrade head` 直接报
`Multiple head revisions are present`。

**当前占用（谁要加新迁移，先看这张表再动手）**

| 编号 | 状态 | 内容 | 接在谁后面 |
|---|---|---|---|
| `0001_planner` | 已合 | planner 行程表 | — |
| `0002_planner` | 已合 | 行程幂等键 | `0001_planner` |
| `0003_catalog` | #87 | catalog 地点与来源 | `0002_planner` |
| `0004_routes` | #91 | routes 草稿表 | `0003_catalog` |
| `0005_identity` | #79 | identity users / sessions | `0004_routes` |
| `0006_planner` | #86 | planner 任务队列 + `agent_steps.step_index` | `0005_identity` |

**取号规矩**：先在表尾领一个号，再写迁移；领号这一步就在同一个 PR 里改这张表。
不领号直接写 `0007_xxx`，下一个人的 `0007` 就跟你撞了。

**两条纪律**

1. **改号只允许在「分支没合并 + 没人在这条分支上跑过这条迁移」的窗口里做。**
   合并之后一律不改编号：已经 `upgrade` 过的库（包括每个人的开发库）里 `alembic_version` 记着旧名字，
   一改名就报 `Can't locate revision identified by ...`，得手动 `alembic stamp` 才救得回来。
2. **main 上万一出现多个 head**，不要回头改历史，用一次合并迁移收口：

   ```bash
   alembic merge -m "merge catalog/planner heads" 0003_catalog 0006_planner
   ```

   生成的那个空迁移 `down_revision` 是元组，把两条链并回一条，历史保持原样。

**本地验证**：用临时库跑往返，别拿自己的开发库试。

```bash
cd services/api
export DATABASE_URL="sqlite:///./_tmp_mig.db"
python -c "from alembic import command; from alembic.config import Config; \
c = Config(); c.set_main_option('script_location', 'migrations'); \
command.upgrade(c, 'head'); command.downgrade(c, '-1'); command.upgrade(c, 'head')"
rm -f _tmp_mig.db      # 跑完删掉，别让它进 git
```

中文 Windows 上直接用 `alembic` 命令会踩 `alembic.ini` 的 GBK 解码坑
（`UnicodeDecodeError: 'gbk' codec can't decode ...`，`PYTHONUTF8=1` 也救不了，
因为 alembic 显式传了 `encoding="locale"`），所以上面用 `python -c` 直接调 `alembic.command`。

## 10. macOS 开发

业务代码与平台无关，差异只在启动脚本和路径上。CI 在 Linux 上跑，合入前以 CI 为准。

### 10.1 一键启动

仓库根有 `启动 CultureWalk.command`，双击即可：首次会建 `services/api/.venv`、装后端依赖、`pnpm -C apps/web install`，然后交给 `scripts/demo_up.sh` 起本地栈。

- 双击提示“无法打开”时，右键 → 打开；或在终端先 `chmod +x "启动 CultureWalk.command"`。
- 它只是把 §1 的手工步骤串起来；出问题时按 §1 一步步跑，更容易看出是哪一步失败。

### 10.2 bash 3.2

macOS 自带 bash 3.2，仓库脚本按 3.2 写。新加 shell 脚本不要用 bash 4+ 语法：

- 关联数组 `declare -A`
- `mapfile` / `readarray`
- `${var,,}`、`${var^^}`
- `&>>`、`wait -n`

`#!/usr/bin/env bash` 在 macOS 上解析到的就是 3.2，别假设用户 `brew install bash` 后就是 5.x。

### 10.3 Python 路径

macOS 的虚拟环境在 `.venv/bin/`，Windows 在 `.venv/Scripts/`；`scripts/preflight.sh` 两个路径都会找。

系统 `python3` 可能是 3.10（Xcode 自带），建环境时显式指定 3.12：

```bash
cd services/api
python3.12 -m venv .venv
. .venv/bin/activate
pip install -e ".[dev]"
```

### 10.4 Docker 与 CPU 架构

Apple Silicon 上 Docker Desktop / OrbStack 默认拉 arm64 镜像，跑 `infra/docker-compose.yml` 没问题。

给 x86 服务器构建镜像时要显式指定架构，否则服务器上会 `exec format error`：

```bash
docker build --platform linux/amd64 -t culturalwalk-api .
```

### 10.5 不要把仓库放在 iCloud Drive

`~/Documents`、`~/Desktop` 可能被 iCloud 同步。仓库里有 `node_modules`、`.venv` 几万个文件，放进去会：

- 同步慢、占双倍空间；
- 文件被“优化存储”驱逐后，构建报莫名其妙的 `ENOENT`；
- `.git` 偶发冲突副本，修起来很麻烦。

建议放 `~/Projects/culturalwalk-platform`。已经放进去的，搬出来后删掉 `.venv` 和 `node_modules` 重装（虚拟环境里记录的是绝对路径）。

### 10.6 大小写不敏感

APFS 默认大小写不敏感，`Foo.vue` 和 `foo.vue` 在 Mac 上看起来是同一个文件，Linux 上是两个。只改文件名大小写时用 `git mv`；这类问题只有 CI 能稳定发现，别跳过 CI。

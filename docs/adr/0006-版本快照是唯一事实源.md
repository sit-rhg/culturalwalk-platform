# ADR-0006：版本快照是唯一事实源，不建 route_version_nodes

- 状态：已接受
- 日期：2026-11-08
- 决策者：P3（routes 模块）

## 背景

`docs/02-数据模型与状态机.md` 曾把 `route_version_nodes` 写成「为查询方便而从 snapshot 展开的只读副本」，
但实现里只有 `route_versions.snapshot`（JSONB），全仓 grep 该表名只出现在文档中。
缺陷收口 B5 要求二选一：补表并回填，或改文档并补 ADR。

## 决策

`route_versions.snapshot`（整份 JSON）是版本内容的**唯一事实源**，不单独建 `route_version_nodes` 表。

- 草稿态编辑读写的节点是 `route_nodes`；
- 提交审核时把草稿节点整体冻结进 `route_versions.snapshot`，并计算 `content_hash`；
- 审核、发布、公开详情都只引用 `version_id + content_hash` 与这份快照。

## 理由

1. **不可变与可审计**：快照 + hash 本身就是「审的就是发的」的证据；拆成两张表后，快照与节点行可能不一致，反而要额外证明一致性。
2. **发布链路不需要节点级 join**：发布绑定的是版本与 hash，详情页读一份 JSON 即可还原整条路线。
3. **体量与成本**：当前是单城、30 个地点、个位数公开路线的演示规模，应用层解析 JSON 足够；加表意味着冻结时双写、迁移回填、以及两处删除/更新的顺序问题。
4. **hash 语义稳定**：`content_hash = sha256(canonical_json(snapshot))` 对整份快照生效，节点表结构变化不会改变 hash 的含义。

## 备选方案

- **A. 建表并回填**：放弃。双写一致性成本、历史数据回填风险都高于收益，且目前的查询需求（列表、详情、筛选）用快照就能满足。
- **B. 只读视图 / 物化视图 `route_version_nodes`**：暂不做。等出现「按地点跨版本聚合」这类真正需要 SQL 连接的需求时，再加一个**派生读模型**，由快照重建，不参与写入。

## 后果

- 正面：版本写入是单行、单事务，没有第二份数据会漂移；答辩可以直接演示「改草稿不影响已冻结版本」。
- 负面：按节点聚合（例如地点热度）要在应用层解析多份 JSON；单版本节点数极大时详情响应会变大。
- 对策：需要节点级查询时新增派生读模型（可从快照异步重建），但派生模型**不得**被当作事实源反向写入。
- 复审时机：出现按地点/主题跨版本聚合的需求，或单版本节点数超过 500。

## 2. 主库发现

### N1 [P1] 发布权限三方不一致

- 规格：`docs/00-总体开发文档.md:52` 管理员行写「审核/发布/下线/管理用户」，编辑行只写「生产/维护平台精选，可审核」——即**发布/下线属于管理员**。
- 现状 A：`services/api/app/modules/moderation/router.py:36-39`
  `ReviewerDep = require_role("editor", "admin")`、`PublisherDep = require_role("editor", "admin")`，上方注释声称「按 docs/00 §5 交给 editor/admin」——文档里没有这条授权。
- 现状 B：PR #195 新增的 `PATCH /places/{place_id}` 用 `user: AdminDep`（`services/api/app/modules/catalog/router.py`），docstring 与 403 说明却写「需要编辑/管理员权限」，测试也用 editor 身份期望 200。
- 后果：editor 现在能发布/下线**路线**，但（#195 合入后）不能发布**点位**；同时 #195 的测试在 rebase 到当前 main（`require_admin` 已在 WP-03 收窄为仅 admin）后会 403 失败。
- 建议：先定口径（建议沿用 docs：路线发布/下线 admin；点位收录状态 editor），然后：
  1. `PublisherDep` 收窄为 `require_role("admin")`；
  2. #195 的 place PATCH 改用 `EditorDep`；
  3. 同步 docs/00 与 authz_matrix。

### N2 [P2] `is_admin()` 与 `require_admin` 语义漂移

- `services/api/app/core/deps.py:39-40`：`is_admin()` 对 editor 返回 True；而 `require_admin` 在 WP-03 后只允许 admin。
- 唯一使用点 `moderation/service.py:543`（他人投稿可见性）语义正确，但后续极易误用。
- 建议：改名 `is_staff()` 或拆 `is_admin()/is_editor()`，并加注释。

### N3 [P2] Idempotency-Key 契约与实现两套口径，且两个 PR 互相冲突

- 契约：`docs/api/openapi.yaml:986` 仍写 `format: uuid`；实现（C8 logout、community 等）是 8–64 任意字符，测试用 `logout-key-0001`。
- PR #182 把契约放宽成 8–64；但 PR #195 的 `planner/router.py::_idempotency_key` 又强制 `uuid.UUID(...)`，非法直接 422。
- 后果：#182 合入后，planner 的 8–64 合法 key 会被 #195 拒掉；两个 PR 同时合 = 契约与实现再次矛盾。
- 建议：#195 去掉 UUID 校验，只保留长度/去空白；或 #182 不改（保持 uuid）——二选一，不要两头都改。

### N4 [P2] 媒体签名器不随后端切换

- `services/api/app/modules/media/adapters/storage.py:126-133`：`get_storage_signer()` 无条件返回 `PlaceholderS3Signer`，docstring 却写「签名与读写必须选同一个后端」；`storage_backend="local"` 时 upload_url 指向 `http://localhost:9000`，本机无此服务。
- 影响面小（前端暂无媒体上传 UI，演示路径不触发），但配置项语义是假的。
- 建议：`get_storage_signer()` 按 `settings.storage_backend` 选实现，local 模式返回本地直传/占位说明。

### N5 [P2] `S3ObjectStore.delete` 用中文字符串判 404

- `services/api/app/modules/media/adapters/objects.py:173-179` 靠 `"返回 404" in str(exc)` 判断「对象本来就不存在」。
- 建议：`ObjectStoreRejected` 带 `status_code` 字段，按码判断。

### N6 [P3] moderation 自建角色 Dep，词汇重复

- `ReviewerDep`/`PublisherDep` 与 WP-03 的 `EditorDep`/`AdminDep` 重复，且角色集合顺序不一致（"editor","admin" vs "admin","editor"）。
- 建议：统一复用 `core.deps` 里的依赖。

### N7 [P1] 停用账号的 access 令牌在 15 分钟内仍可访问业务端点

来源：identity 子 agent 复审（`_tmp/review_identity.md`，探针可复现）。

- `services/api/app/core/deps.py:87-105` 的 `_user_from_auth_header` 只用令牌 claims 组装 `CurrentUser`，只查会话是否被撤销，**从不查 users 表**；账号状态校验只存在于 `/users/me`（`identity/router.py:107-109`）和公开主页。
- 实测：账号 `status=disabled` 后，`/api/v1/users/me=401`，但 `/api/v1/notifications=200`、`/api/v1/plans=200`；窗口 = access TTL（默认 900s）。refresh 已拦住（`identity/service.py:177-179`），所以最长 15 分钟自然失效。
- 建议：把账号状态纳入统一身份校验（`session_is_revoked` 顺带查 users，或 `_assert_session_active` 后补 `db.get(User)`），停用流程同时 `revoke_all_for_user`；补「停用后业务端点 401」测试。

### N8 [P2] 同 sid 并发 logout 非 CAS：双审计 + 覆盖 revoked_at

- `identity/service.py:226-233` + `identity/repository.py:114-116`：两个并发 logout 都读到 `revoked_at is None`，都返回 1，写 2 条 `auth.logout`，后写覆盖 `revoked_at`。
- refresh 已改用条件更新 `revoke_if_active`，logout 没跟上。建议 logout 也走 `revoke_if_active`，`rowcount == 1` 才写审计。

### N9 [P2] refresh 重放审计可放大

- `identity/service.py:194-199`：同一枚已轮换的旧 refresh 每次重放都写一条 `auth.refresh_reuse`，即使本次 `revoke_all_for_user` 返回 0。探针连打 3 次 = 3 行（后两行「已撤销 0 个会话」）；令牌 14 天有效期内可无限放大。
- 建议：只在 `revoked > 0` 时写审计（或首次命中写一条、后续计数）；该路径加限流。

### N10 [P2] 轮换无宽限窗口：合法重试/双标签并发会撤全家（需产品定夺）

- `identity/service.py:171-173`：轮换后的旧 refresh 重放与「合法客户端超时重试/双标签并发」无法区分，后到者摘要不匹配 → 撤销该用户全部会话，先到者刚拿到的 200 新令牌也立刻失效；`test_auth_api.py:363-374` 已把该行为固化为期望。
- 二选一：给 10–30s 宽限（窗口内旧摘要重放只 401、不撤家族），或前端 refresh 单飞/串行化；维持现状则在契约/文档写明「并发刷新会导致全端重登」。

### N11 [P2] 两处安全审计缺 actor 字段

- `identity/service.py:194-199`、`:235-240`：`auth.refresh_reuse` / `auth.logout` 的 `actor_id`、`actor_username` 为空，而 user id 就在参数里；其它模块都填了（community/moderation/catalog）。
- 建议：补 `actor_id`（logout 再补 `actor_username`）。

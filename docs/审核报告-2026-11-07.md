## 2. P0

### 2.1 媒体：幂等重放 intent 会按 clean 前缀重新签名，绕过扫描

- 位置：`services/api/app/modules/media/service.py:91-95`（重放分支）、`:384-390`（`_intent_out` 用当前 `object_key` 签名）、`:288`（扫描通过后 key 从 `quarantine/` 改成 `clean/`）、`adapters/storage.py:78-90`（policy 对 key 精确绑定）
- 现象：首次 `POST /media/intent` 拿到 900s 有效的上传票；扫描通过后 `object_key` 变成 `clean/...`。在过期前用**同一个 Idempotency-Key** 再 POST，`create_intent` 命中 `existing` 直接 `_intent_out(existing)`，于是拿到一张**绑定 clean 路径**的可写 POST policy —— 可直接覆盖已扫描通过的 clean 对象，绕过隔离区 + 扫描。
- 根因：幂等重放只看 `owner_id + idempotency_key`，不看 `scan_state`/`zone`；`_intent_out` 无条件按当前 key 签名。
- 建议：仅在 `scan_state is PENDING` 且未过期时重放上传票；`SCANNING/CLEAN/REJECTED` 返回资产当前状态（或 409 `MEDIA_ALREADY_UPLOADED`），任何情况下都不对非 `quarantine/` 前缀签名。
- 备注：当前 `get_storage_signer()` 恒返回 `PlaceholderS3Signer`（见 3.6），真实 S3/MinIO 不认，所以线上暂时打不通；但这是逻辑漏洞，接真存储那天立即生效。

## 3. P1（按模块）

### 3.1 core / audit / discovery

**3.1.1 默认 JWT 密钥，且令牌不要求 exp，可伪造永久 admin 令牌**
- `core/config.py:25` `jwt_secret` 默认写死 `"dev-only-change-me"`；`core/deps.py:48-52` `jwt.decode` 只验签名，实测 HS256 且无 `exp` 的令牌被接受；`sub/username/role` 全取自令牌，`role=admin` 立即生效。
- `settings.env`（`config.py:16`）声明了但全仓零使用，也没有启动期密钥校验；`infra/.env.example` 还把这个默认串当示例。
- 建议：非 local 环境启动断言密钥非默认值；`decode` 强制 `exp`（`options={"require_exp": True}`）；密钥只从 env 注入。

**3.1.2 `get_db` 在响应发出后才 commit，提交失败静默丢数据**
- `core/db.py:30-40`：`yield db` 之后才 `db.commit()`。FastAPI 的 yield 依赖退出代码在响应发送**之后**执行；commit 抛错（约束/死锁/断连）时客户端已收到 2xx，事务实际回滚。
- 实测（本机最小复现）：teardown 抛 `RuntimeError` 的依赖，handler 返回 500，客户端实际收到 `STATUS 200 BODY {"saved":true}`。
- 业务 service 普遍只 `flush` 不 `commit`，完全依赖这个 teardown（audit 等模块）→ 影响面是全仓写接口。
- 建议：路由返回前显式提交（service 层 commit，或请求级事务中间件包住 handler）；测试走真实 `get_db`。

**3.1.3 access token 不校验会话吊销 / 账号状态**
- `core/deps.py:55-69` 只解 JWT，不查 `sid` 对应 session 是否已 revoke，也不查 user.status/role 是否仍有效；`identity/service.py:167-190` 的 logout 只把 session 行标记吊销。
- 后果：登出后旧 access token 在 900s 内照常可用（实测 `/users/me` 仍 200）；封号/降权同理。
- 建议：敏感端点在 `require_user` 里按 `sid` 查一次 `sessions.revoked_at`（主键查询），或加 `users.token_version` 并在 JWT 带 `sv`；至少在 docs/03 明示这个窗口。

### 3.2 identity

**3.2.1 用户名长度校验发生在 strip 之前，空白/过短用户名能落库**
- `identity/schemas.py:19` `Field(min_length=3, max_length=24)` 按**未 strip 的原始串**判长度；`identity/service.py:117` 之后才 `strip().lower()`，归一化后无人复核。
- 实测：`{"username":"   "}` → 201 且 `username == ""`；`{"username":"  ab  "}` → 201 且 `"ab"`。唯一索引只保证空串能存在一次。
- 建议：`Annotated[str, StringConstraints(strip_whitespace=True, min_length=3, max_length=24)]`（pydantic v2 先 strip 后判长度），或在 normalize 后显式复核。
- 测试假绿：`identity/tests/test_auth_api.py:49-58` 用 `"  Ming  "` 断言 `username == "ming"`，把「strip 在校验之后」固化成期望。

**3.2.2 重复邮箱被报成「这个用户名已经被注册了」**
- `identity/service.py:118-134`：只对 username 做预检，`except IntegrityError` 把所有唯一约束冲突都翻成同一条 username 文案，不解析约束名，也不回传 `details.field`。
- 实测：用户 1 用 `a@b.com` 注册成功后，用户 2 用 `A@B.com`（用户名全新）→ 409「这个用户名已经被注册了」。
- 后果：用户按提示改用户名永远改不好；也构成「该邮箱已注册」的 oracle。
- 建议：按 `exc.orig` 约束名分流（PG `uq_users_email_lower` / `uq_users_username_lower`；SQLite `users.email` / `users.username`），两条 Conflict 文案分开并带 `details={"field": ...}`。

### 3.4 media（其余）

**3.4.1 `complete` 不验证对象存在，可永久堵死扫描队列**
- `media/service.py:147-152` 只把状态改成 SCANNING，不查对象是否存在/大小是否符；扫描时缺对象抛 `MEDIA_OBJECT_MISSING`，被 `scan_pending` 计入 skipped 且状态不回退；`list_scanning` 按 `created_at` 升序取前 N 条 → 队头永远先被取到。
- 后果：任何登录用户 intent→complete（不传文件）重复 10 次即占满默认 `limit=10`，之后所有资产都扫不到。
- 建议：`complete` 时 `store.exists` + 大小校验（不符 409/422）；扫描失败计数，超 N 次转 REJECTED 或按失败次数重排。

**3.4.2 `mark_clean` 允许 PENDING 直达 CLEAN（跳过上传与扫描）**
- `media/service.py:190-204` 只挡 REJECTED；PENDING/SCANNING 都能直接置 CLEAN、`zone=clean` 并写入公开 url（此时 `object_key` 仍指向 `quarantine/...`）。`mark_rejected`（`:228-235`）同样允许 PENDING。
- 建议：要求 `scan_state is SCANNING` 且 `completed_at` 非空，否则 409 `MEDIA_NOT_UPLOADED`。

**3.4.3 先全量解码后校验尺寸，图片炸弹可致内存耗尽**
- `media/scan.py:76` 的 `image.load()` 在 `:86-91` 的 `MAX_SIDE/MAX_PIXELS` 检查**之前**；12000×12000=144MP RGB ≈ 432MB，而 Pillow 默认只在 >~178.9MP 才抛 `DecompressionBombError`（144MP 仅告警），本模块上限内仍会完整解码；异常捕获列表（`:71`、`:101`）不含 `DecompressionBombError`。
- 建议：`open` 后用 `image.size` 先判尺寸再 `load`；设 `Image.MAX_IMAGE_PIXELS`；捕获 `DecompressionBombError/Warning`。

## 3.9 routes

**3.9.1 费用区间可汇总出 min_total > max_total**
- `core/costing.py:22-34`（routes 调用点 `routes/service.py:539-550`）：节点 A 只有 `price_min=1000`、节点 B 只有 `price_max=50` 时，`summarize_cost` 返回 `min_total=1000, max_total=50, unknown_count=2` —— 最低价大于最高价。

## 3.10 moderation

**3.10.1 发布缺少并发互斥，同一投稿可产生两条 PUBLISHED，下线失效**
- `moderation/service.py:544-563`（check-then-insert）、`models.py:193-199`、`repository.py:231-237`：两个**不同 Idempotency-Key** 的发布请求同时通过「无已发布」检查，各自插入 Publication；`publications` 表没有 docs/02 §5 line 248 要求的部分唯一索引 `(route_id) WHERE state='PUBLISHED'`（`repository.py:232` docstring 自述「只能应用层挡」）。

- 建议：加部分唯一索引 + 捕获 IntegrityError → 409；首次发布用行锁/草稿锁串行化 route_id 分配。

### 7.3 #22 的 500 根因（新发现，建议优先修）

`claim_cas`（`moderation/repository.py:114-152`）与 `reclaim_expired`（`:92-112`）的 WHERE 都含 `lease_expires_at < now`，`now` 是 aware UTC，而 SQLite 把 `DateTime(timezone=True)`（`models.py:151-153`）读回 naive；ORM 批量 UPDATE 默认 `synchronize_session="auto"`，会对 Session 里已加载的任务对象做 Python 侧求值，抛 `TypeError: can't compare offset-naive and offset-aware datetimes` → 500。

- 触发条件：任何「任务已读进本请求 Session 且处于 CLAIMED」的领取/释放/决定/撤回。
- 为什么测试绿：`test_workflow_api.py:450`、`:474` 直接往共享 Session 的对象里写 aware 值，绕开了读回路径；模块内 `grep TASK_ALREADY_CLAIMED` 0 命中。
- 修法：CAS UPDATE 统一 `.execution_options(synchronize_session=False)`；补「先提交再领取 → 409」「过期后 claim/decide/withdraw」用例。
